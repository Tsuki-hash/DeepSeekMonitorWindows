# 第 29 轮：历史缓存失败状态跨导航与重挂载

**本轮仅修改源码、补回归用例并静态审阅。未编译，未执行类型检查、测试、脚本或应用，也没有 Windows/WebView2 验收结果。以下均为维护者待执行步骤，不是通过记录。**

## 修复契约

- 缓存以当前用量 Token 的 epoch 和月份隔离。成功数据与最新失败状态分开保存：强制刷新失败后，普通读取不能仅因旧成功仍在五分钟 TTL 内，就把它返回为本次成功。切换范围、退出历史后重挂载以及局部 state 重置均不清除失败。
- 失败携带原有错误分类，完整错误仅瞬时用于分类；缓存只保留分类、月份和固定安全文案，不保留原错误文本、任意错误对象或附带的完整响应。IPC/网络/解析错误没有统一脱敏保证，截断也不能确保不留下凭据或响应原文。`not_configured` / `credentials_invalid` 继续提供配置或重新同步 Token 入口；限流和暂时不可用继续停止本批；月级错误继续其他月份。`invalid_data` 提到 Token 时仍是月级错误，旧 `unknown` 鉴权文案仍能识别。
- 完整月响应仍最多缓存四个月，不因失败无限保留。失败元数据和“曾成功但旧数据已逐出”状态不随 payload 淘汰而清除。仍在缓存中的旧成功数据可恢复为陈旧记录；已逐出的数据不伪造为零或成功，面板明确提示“旧成功缓存已释放”，保留失败和真实重试入口。同一挂载面板已有的范围快照仍按既有规则保留。
- 已有成功历史的失败在五分钟失败 TTL 内按原状态恢复；TTL 到期或当前月跨记账日后，普通查询可以真实请求，但到期、跨日、请求开始本身均不清错。首次从未成功的月份仍沿用普通查询发起真实请求的既有行为。显式“只重试失败月份”和顶部重新查询始终绕过缓存发出真实请求。
- `HistoryPanel` 将缓存携带的旧成功放入已保留数据，而非本轮成功集合。失败可与旧数据同时存在。只有真实 loader 成功才能清除同代同月失败；页面和 JSON 的 `failedMonths`、JSON/CSV 的 `stale` 不因切范围或重挂被清空。CSV 原有正常/未知记录语义保留，JSON 继续区分失败、未加载和缺失日期。
- 强刷不被 pending 去重吞掉。普通新消费者先共享最新在途请求。每次新请求替代该月份所有尚未结束的旧请求；旧响应只跟随最新结果，不写回缓存。覆盖 A 在途、B 完成、C 再开始、A 最后返回的交错，而非只防两个同时在途请求。旧失败不能覆盖新成功，旧成功也不能抹掉新失败。
- 更换或清除 Token 同时清除成功缓存、失败元数据及请求归属；旧 epoch 尚未启动的 loader 不再开始，已经发出的旧响应不能进入新账户。面板原有停止、隐藏、范围变化及卸载所有权检查继续生效；取消后的晚到结果不能直接修改已提交页面或导出。
- 本轮日期证据修复在面板增加可展开的异常日期数量、原始日期、查询月份及理由。它们不进入正常合计，原始证据随导出保留，具体日期与导出契约见同轮日期回归文档。

### 生产面板和导出

`tests/history-lifecycle.test.tsx` 使用现有 legacy/concurrent renderer 两种模式，挂载生产 `HistoryPanel`、生产缓存和生产导出逻辑，只有 IPC 响应和时钟为合成夹具。新增：

1. 未配置、凭据失效、限流、服务不可用、月级数据错误、普通未知错误与旧鉴权提示，分别走“真实成功 → 强刷失败 → 上月 → 本月 → 卸载重挂 → 真正重试成功”。重挂前把 loader 改为健康，断言未调用它就不能宣称恢复；核对旧数据和原始来源时间不改、恢复按钮、JSON `failedMonths/stale` 以及 CSV `stale`。
2. 全部历史的成功数据先超过缓存容量，再刷新失败。同页保留原快照；重挂到本月后原 payload 已逐出，应显示未知和明确说明，不生成零值，真实重试才恢复。
3. 同时存在成功、失败和更早未加载月份，切换/重挂后保持各自口径；重试只请求失败月份，不擅自扩大到整段历史。
4. TTL 到期与同月跨记账日允许真实请求；若新请求仍失败，失败状态保持；在途重试期间导出不可用，真实成功后才清错。
5. 重挂共享已开始的重试；随后换 Token，新账户成功后再释放旧账户迟到成功或失败，当前页面和再次重挂结果都不能污染。
6. 确认异常日期在页面可见，正常指标和日记录不混入异常来源。CSV 检查使用引号/转义感知的解析，不能把带引号的布尔值或含逗号的证据误读。
