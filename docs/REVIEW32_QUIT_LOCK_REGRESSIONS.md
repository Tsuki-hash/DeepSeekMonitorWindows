# R32 退出交互锁与异步保存回归

## 修复范围

- `confirm_quit` 发出前同步锁住编辑与导航，拦住尚未重新渲染的保留回调与真实 DOM 输入事件。失败解锁，成功保持锁定。
- 锁代际永久撤销此前捕获的剪贴板读取、凭据准备保存和设置页组合保存。退出失败后，旧续作也不能重新取得执行权。
- Key 和 Token 保存可能等在 Clear 队列后，因此在真正发送 IPC 的回调中再次检查原始锁代际与页面/操作所有权。
- 网页登录也可能排在跨页面的全局 Clear 队列后；真正启动前检查原始锁代际、页面和会话所有权。被撤销的排队登录只释放自身进度，不在失败解锁后启动窗口，也不显示内部撤销异常。
- 已经进入原生层的保存仍接收并同步可信配置回执；被撤销的旧会话不消耗新草稿，不继续下一项保存，不发第二次退出。busy 清理仍按原始操作所有权进行。

## 已编写、尚未执行的自动回归

`tests/quit-request-lifecycle.test.tsx` 使用真实 App、SettingsPanel、草稿协商和退出 hook，延迟模拟原生 IPC。以下场景均覆盖 legacy/concurrent renderer 与 StrictMode 包装：

1. 退出 IPC 内、React 重新提交之前，调用保留的 API Key、Token、提醒、保存和返回回调，确认不产生新草稿、不导航、不重复提交；失败后新编辑恢复。
2. 退出前发起剪贴板读取，退出失败后才返回，确认旧读取不产生草稿。
3. Key＋Token＋提醒，或 Token＋提醒，保存第一项时取消离开，再选择放弃并退出。分别在退出仍在途和已经失败解锁时返回旧保存，确认后续 Token/提醒不发送、提示不复活、退出不重复。
4. Key/Token 保存先排在对应 Clear barrier 后，取消离开再放弃并退出，随后释放 Clear。分别验证退出仍在途与失败解锁后，旧候选从未发送到保存 IPC。
5. 上述失败路径清理完成后，显式编辑和保存新 Token/Key 能正常执行，不会卡住 busy。
6. 旧设置页清除 Token，在清除未完成时离页重入并请求网页登录，使登录排在全局 Clear barrier 后。退出在途/失败解锁与 Clear 成功/失败两两组合，确认旧登录从未发 IPC、Clear 仍按原路径结算且成功回执更新已提交配置、同步按钮正常复位；退出失败后新显式登录仍可启动。

另有同步 gate/owner 单元测试和原生事件围栏的合成节点回归。组件 suite 已在 `scripts/test-settings-components.mjs` 的现有入口中，不另设旁路 runner。

## 待执行验收与边界

本轮只做静态读改，未运行测试、构建、脚本或应用。仍需执行项目正式类型、单元、组件及完整发布门禁；合成 renderer 不能证明 Windows/WebView2 的 inert、真实键鼠输入、焦点或原生退出行为。

Windows 验收应在保存/退出人工延迟下重复上述流程，特别确认退出期间无可编辑输入、恢复状态可读、退出失败能继续编辑，以及旧保存不引出第二个写操作。已发出的原生事务无法由前端锁撤回；本修复不取消用户此前已请求的清除/忘记账户隐私操作。
