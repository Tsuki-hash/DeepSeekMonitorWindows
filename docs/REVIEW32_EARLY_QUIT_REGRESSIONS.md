# R32：退出监听就绪前的托盘退出意图

本轮仅静态阅读与修改源码。下列测试已补入，但没有执行项目测试、构建、脚本或应用；也未完成 Windows / WebView2 实测。

## 问题与实现

原生托盘成功恢复主窗口后只发送一次 `quit-requested`。前端监听尚未安装时，事件即使发送成功，也不会在监听就绪后重放，退出请求会静默丢失。

- 原生 `QuitIntent` 在进程内保留单调 `issued` / `acknowledged` 序号。托盘先登记意图，再发送仅用于唤醒的事件。状态由 Builder 管理，独立于托盘菜单和前端监听是否就绪。
- 主窗口安装监听后调用 `get_pending_quit_intent`。读取不消费意图；卸载后迟到的读取结果不确认接收，新 owner 仍可读取。所有接收仍走 `requestQuit → navigate → 草稿协商 → confirm_quit`。
- 前端在进入草稿协商前记录已消费序号，随后调用 `acknowledge_quit_intent`。选择留在此页也消费该次意图，旧 wake、重复快照、ack 失败重试或 StrictEffects owner 重建不再次打开同一次协商。
- 读取期间收到 wake 会再读一次。原生只确认指定序号，旧 ack 不清除更新点击，较旧快照不回退消费水位。序号以十进制字符串传输、BigInt 比较，避免 JavaScript 整数精度丢失。
- 注册、初次读取或后续读取/ack 失败均展示恢复入口并解除当前监听；重试后继续检查原生未消费请求，不直接使用旧的退出批准回调。
- 两个新命令均先校验 `require_main`。托盘找不到主窗口时记录失败，不再直接 `app.exit(0)` 绕过草稿协商。

这里的持久状态是进程生命周期内的内存状态，不写磁盘，也不跨应用重启重放退出请求。前端消费水位跨同一 WebView 中的 effect/owner 重建保留；原生 ack 成功后也不会因 WebView 重载重放。进程崩溃或 WebView 在草稿接收与 ack 完成之间被强制销毁，不属于已验证的 exactly-once 事务保证。

## 待本机验证

1. 延迟前端监听注册，在托盘可操作后立即点退出。监听成功后，应只进入一次当前草稿协商；无草稿时确认退出。
2. 注册或 IPC 读取失败时，应显示恢复入口。重试后处理尚未接收的请求，不能要求用户凭猜测补点退出。
3. 留在此页后发送旧 wake、重复快照及重试 ack，不再弹出旧协商；新托盘点击仍可再次协商。
4. 延迟读取/ack，交错新点击、组件卸载/重新挂载及退出命令失败，确认旧响应不夺取当前 owner、不复用旧批准、不重复提交退出。
5. Windows 主窗口恢复失败或缺失时不得原生直接退出；实际托盘显示、焦点、冷启动和 WebView2 IPC 时序仍需实机验收。
