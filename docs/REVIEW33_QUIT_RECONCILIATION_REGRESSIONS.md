# R33：退出监听就绪后的丢事件恢复

本轮仅修改和静态审阅源码。以下回归已补入，但没有运行测试、构建、脚本或应用；没有完成 Windows / WebView2 实测。

## 问题

R32 在原生保留退出意图，并在监听安装后补取。但首次补取完成后，如果托盘已经 publish 而 `quit-requested` 的 emit 失败或事件没有交付，前端仍处于 ready/idle。没有新的 wake 就没有新的读取，也不会显示恢复入口，一次退出点击会一直悬置。

## 修复

- `QuitRequest` 在带 mailbox 的监听进入 ready 后启动一个 2 秒对账定时器。事件仍用于尽快响应，对账不依赖下一次托盘点击或事件。
- 事件与定时器共用同一个 drain。对账遇到在途读取或 ack 时只标记需要补读，不发起并行读取；完成后才安排下一次定时器。浏览器调度可能延迟执行，2 秒是调度间隔，不是硬性时限。
- 对账仍调用 `QuitIntentMailbox.consume → requestQuit → navigate → 草稿协商`。消费水位、字符串序号和指定序号 ack 不变；选择留在此页后，重复对账不会复活同一次意图。
- 注册中不轮询；读取/ack 失败会撤销定时器与监听并显示既有恢复入口。用户重试成功后重新开始对账，不默默吞掉同步错误。
- 卸载、监听重建和确认退出会撤销定时器身份。即使宿主迟到交付已取消的回调，它也不能发起读取、删除新一代定时器或重新排程。确认退出也立即撤销在途对账的 owner：晚到读取不消费或 ack 新意图，晚失败不发布恢复状态；已经发送的 ack 可以结束，但不能改变终态或恢复定时器。
- hook 显式使用 WebView 的计时器；纯函数测试注入可手动推进的假时钟。本项退出对账修复没有修改原生命令权限或提醒保存逻辑；R33 整合中的提醒保存修复属于另一项独立改动。
